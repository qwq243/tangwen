# 埋点与后台

## 埋点记了什么

**前端只记「什么事件发生了几次」。不记问题原文、不记 IP、不记 UA、不记设备。**

事件七种：`pv`（开卷成功）、`ask`、`hint`、`solve`、`give`，
以及为「模型调用」加的两档 `judgefail`（判题调用失败）、`hintfallback`（求灯退到兜底）。
按模型的求灯次数不进事件表，它是当天的一张小字典（`day.m`）。

**但事件不在同一个地方记**：

| 事件 | 谁记 | 记在哪 |
|---|---|---|
| `pv` | 客户端 | `web/app.js` 的 `track()`，攒批走 `/api/track` |
| 其余六档与 `day.m` | 服务端 | 各自接口里自己数：`bump_track()` / `bumpTrack()` |

**为什么这几档改成服务端数**：曾经报过「后台好像不能正常更新，提问之类的没记录」——
那几档原本写在客户端，而线上跑着的是**旧的 `app.js`**（页面改动要等下一次部署才生效），
于是后台的提问、求灯、结案整天是 0，访问量却照常涨（实况 `pv=67 uv=22 ask=0`），
看着像后台坏了。判题、求灯、放弃这些服务端本来就知道的事，不该由页面转述。
`tools/track-check.mjs` 钉住这条（还顺便钉住「两边都记就是记双」）。

**模型调用那两档走同一条路**：它们也只有服务端知道（判题挂了、模型链退到头了），
而且**必须跟主计数并进同一次 KV 写** —— 为了多记一个数再读-改-写一次 KV 不划算，
免费额度是按写次数算的。

**以后加新事件先问一句：服务端自己看得见吗？** 看得见就写进接口，看不见才写客户端
（比如「这一卷在浏览器里真的开出来了」只有页面知道）。

`pv` 是**攒批发**：攒够 20 秒、或者页面要走了（`pagehide` / 切到后台）才 POST 一次，
一次会话通常只写 1~3 次 KV —— 一条事件发一次请求的话，云那边一天几千次 KV 写直接顶到
免费额度。**页面要走了那一次必须走 `navigator.sendBeacon`**：普通 `fetch` 在这个时机
会被浏览器直接掐掉，而结案恰好是「看完就走」的场景，会整批丢光。

## 每日统计

服务端按 **Asia/Shanghai** 切日聚合进 KV 命名空间 `BOARD`：

| 键 | 内容 | 说明 |
|---|---|---|
| `st:d:YYYY-MM-DD` | `{"c":{pv,uv,new,ask,hint,solve,give},"p":{"<卷id>":{ask,hint,solve}}}` | 当日计数 + 分卷明细 |
| `st:u:YYYY-MM-DD` | `["<uid>", ...]` | 当日出现过的 uid，只用于 UV 去重，60 天自清，单键最多留 3000 个 |
| `st:f:<uid>` | `"YYYY-MM-DD"` | 该 uid 首次出现日，用来算「新增」 |

日期一定要按 +8 切：Worker 跑在 UTC，直接取 UTC 日期的话北京时间 00:00–08:00 的访问
会记到前一天去，国内站点这是肉眼可见的错。

uid 就是排行榜那个 `player.id`（浏览器本地随机生成），跟人没有对应关系；
`st:f:` 里也只留「这串随机数第一次来是哪天」。

**已知偏差，别当精确账**：日计数是「读-改-写」，同一天的请求并发撞在一起时会少记几笔；
KV 本身也是最终一致（跨机房最长 60 秒）。看趋势够用。

**服务端自己数那几档的代价**：每问一次多一对 KV 读+写（原先一整个会话才写 1~3 次）。
这个量级跟「每问一次就要调一次判题模型」比可以忽略 —— 出得起模型调用，就出得起这一笔。
反过来才是要防的：判题失败（模型挂了、超时）**也照样记这一问**，不然上游一挂，
后台看起来就是「今天没人提问」。`tools/admin-check.py` 有一条用例专门钉这个。

## 后台（账房）

地址 `/admin/`。零依赖单页，图是手写 SVG（为三条折线引一整个图表库不划算）。
页面**不从任何地方链过去**，地址记在这儿就行 —— 真正的门是密钥。

**登录**用的是 `ADMIN_KEY`（两边命名一样，自建走环境变量，Pages 走 Secret）。
`POST /api/admin/login` 常数时间比对，成功后发一个 **HMAC-SHA256 签名的自包含 token**，
有效期 12 小时 —— payload 里只有过期时间戳，服务端不存会话表，也就没有会话要清理。
token 放 `sessionStorage`，关标签页即失效。限流是同一 IP 15 分钟内连错 8 次锁死，
**锁住期间对的密钥也进不去**，防爆破优先。

没配密钥的话 `/api/admin/probe` 回 `configured: false`，登录页会把这句话直接顶在提示里，
不会让人对着「密钥不对」猜半天。

**会自己转**：进来之后每 30 秒拉一次统计（只拉统计，不重画卷宗那份 44 条 `<details>` ——
重画会把展开的收回去、把滚动位置顶掉，而卷宗本来就随包发布、不会变）。切到别的标签页就停，
切回来立刻补一次。以前只有「进页面」和「点刷新」两个时刻会取数，玩家提问之后不点一下，
看到的就是几分钟前的数，很容易误判成「后台没在记」。

**能看**：近 7/14/30/90 天趋势与汇总、分卷明细、近 7 日逐日、模型调用、
44 卷汤底与关键点核对（每卷那行挂着卷 id、汤色、难度、关键点数四枚签）、导出 JSON。
**能改**：排行榜删单条、清空本卷。

卷宗核对能搜能筛：顶上一条搜索框加一排分类 chip（全部 / 清汤 / 红汤 / 黑汤 ｜ 浅 / 中 / 深，
各带全库卷数）。搜索覆盖**整卷正文** —— 卷名、卷号、汤面、汤底、关键点的标题与问法，
空格分开的多个词是「都要命中」（AND）。两类分类是并列的、能叠（「黑汤 + 深」）。
卷尾计数写成 `N / 44 卷`，但**卷号仍是全库里的号**（筛出「第 07 卷」跟在卷面上看到的是
同一个 07）—— 核对时说的卷号不能跟着筛选漂。只搜标题是不够的：核对的场景常常是
「我记得有个词，在哪一卷来着」，那个词多半在汤底里。

### 模型调用卡

五格：判题调用 / 判题失败 / 讲对了没结案 / 求灯调用 / 求灯兜底，各带今日与区间合计。
失败、兜底、「讲对了没结案」不为 0 时标红。下面一张表按模型分解求灯次数与占比。

| 数 | 怎么来的 | 它出问题长什么样 |
|---|---|---|
| `ask` | 每次通过校验的 `/api/ask` 一笔 | —— |
| `judgefail` | 判题调用抛错（HTTPError / 超时 / 其它）各一笔 | 问什么都答不上来，而「提问」照涨 |
| `hint` | 每次成功的 `/api/hint` 一笔 | —— |
| `day.m[模型]` | 求灯这一句**实际是谁答的** | 主力模型下线时，表里只剩备胎那行 |
| `hintfallback` | `model` 是空串（AI 没绑 / 模型链全挂 / 撞泄底闸退到头） | 「求灯永远同一句话」，以前后台一点痕迹都没有 |
| `nearmiss` | 机制说对了却没被当成整段汤底讲，于是没结案 | **应当恒为 0**。涨起来就是结案判据又在拿语气或措辞判事，玩家看到的是「我都答出来了它却不结案」 |

**判题那条不按模型记**：模型是写死的 `jev-latest`，而且每次提问必发一次调用 ——
所以「判题调用次数」就等于提问数，多记一笔是重复计。它和 `judgefail` 的差就是
「模型调用没回来」的那些。`stats` 响应里另带 `judge_model`，卡片把它摆出来核对
（换模型是静默故障）。

### 后台自己的两处硬约束

都在 `tools/admin-shot.mjs` 里钉着。

**图不能被缩放**：`viewBox` 必须按容器**实测像素宽度**画（`viewBox="0 0 W H"` 且
`W == 渲染宽度`）。早先写法是 viewBox 钉死 1000 宽再让 SVG 整体缩放，390 宽的手机上
12px 的刻度被缩成 3.7px —— 等于没有刻度。窗口尺寸变了要重画（防抖 160ms）。

**卷宗要先于统计取**：`loadAll()` 里 `await loadVolumes()` 再 `await loadStats()`，串行。
并行的话统计先回来、卷宗还是空的，排行榜下拉和表就一直是白的，而没人会再触发一次填充。
这个竞态在 390 宽的手机视图上必现，1440 桌面上偶尔能赢 —— 是最难查的那种**假绿**。

## 验收

```bash
python tools/admin-check.py                                     # 接口回归，自带服务与临时数据目录
node tools/admin-shot.mjs http://127.0.0.1:8765/ <ADMIN_KEY>    # 界面自查，真登录取 token
node tools/track-check.mjs http://127.0.0.1:8765/               # 埋点，真问一句看后台记到没
```

`admin-check.py` 有 49 条断言：埋点聚合（含判题失败、求灯按模型记、兜底那一档、
「讲对了没结案」那一档、关键点自己讲出来那一路）、UV 去重、登录限流、token 过期与篡改、
排行榜删档、卷宗带汤色。
